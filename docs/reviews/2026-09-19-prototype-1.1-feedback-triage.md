## How to use this doc

- **Kind + target skill** tells you whether a row is `/feedback` (an
  observation) or `/requirement` (asking the spec itself to change). Filing a
  requirement-shaped item through `/feedback` will get it filed, but triage
  will just have to reclassify it — do it right the first time.
- **Related FR/SC** is only ever a *pointer* — checked against
  [`specs/001-student-mvp1-delta/traceability.md`](../../specs/001-student-mvp1-delta/traceability.md)
  just now, never invented. Where a row cites one, say so explicitly when
  filing (`/feedback` step 2 asks for exactly this).
- **Quadrant** is engineering-execution guidance (parallel safety), not a
  triage outcome. It answers "who can pick this up and when," not "should we
  build it."

**Correction (2026-09-19, same day):** row 021 was marked done below and
closed on GitHub as #25 — wrong, per Tamer. What exists (`ResumePrompt` +
`sessionStorage` in `LessonSession.tsx`, text fixed in `73c30a8`) is not what
was asked for, on two counts: (1) `sessionStorage` doesn't persist across
sessions — it survives a reload of the same tab, not a student coming back
later or on another device, which is the actual ask; (2) the intended
behavior isn't "silently reload the exact frame" at all — it's ask a couple
of quick revision questions to reactivate the material, *then* continue.
Reopened on GitHub with both gaps recorded; no implementation attempted here
per instruction.

**Further update, same day — 021 is blocked, not just scoped bigger.** Traced
why durable per-student persistence can't just be bolted onto today's
`students.id`: it's a Postgres `GENERATED ALWAYS AS IDENTITY` sequence, local
to whichever environment's DB it lives in ([`db/schema.sql`](../../db/schema.sql)),
and `load_seed.py`'s normal full-content-reload path
(`TRUNCATE ... students ... RESTART IDENTITY CASCADE`, no `--course` flag)
wipes the table and cascades the delete through `attempts`, `mastery`, and
`sessions`, restarting ids from 1 — a routine content-reseed operation, not a
rare one. On top of that the id is bound to a plain, non-httpOnly,
client-editable cookie that [`lib/demo-student.ts`](../../app/src/lib/demo-student.ts)
itself documents as "NOT an identity claim and NOT a security boundary."
Persisting real lesson history against this id would be silently deleted by
routine reseeds and readable/writable by anyone who edits the cookie.
**021 is now recorded as blocked on the accounts/auth bundle (rows 002–007,
FR-106, currently DEFERRED)** — that work is what introduces a student
identity stable independent of the curriculum-content lifecycle and actually
bound to a person, which durable resume needs as a precondition, not as a
nice-to-have. Sequencing, not scope, was the missing piece in the note above.
