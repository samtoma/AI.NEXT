Ten fixes, and four requirements that were lying

The first Student MVP release shaped by someone using the product instead of building it. Tamer ran v0.2.0 as a student would, filed 37 issues, and four requirements marked VERIFIED failed in front of him. This is every change in the release: what he saw, what was actually wrong, and what changed.

The defects

On almost every one of these, the symptom that was reported and the thing that was actually broken were in different files. That gap is why each entry below separates them.

A correct answer was marked wrong for showing the working

#40FR-C03
He saw
Typing 3x6 for a question whose answer is 18 was graded wrong.
Actually wrong
Grading used parseFloat, which silently reads only the leading digits and discards the rest. 3x6 was compared to 18 as the number 3. The same flaw ran the other way too: for an answer of 3, typing 3x6 was graded correct.
Changed
Grading now tries, in order: an exact numeric literal, then evaluating the expression, then the old lenient parse, then string equality. The evaluator is a hand-written recursive-descent parser over a whitelisted character set — deliberately not eval or Function, since this parses text a student typed — and it adds no model call to the grading path.
Proof
5 new unit tests. Checked live against q:u1-1-2:g002-cardin: 3x6 correct, 3x5 wrong and still diagnosed as the product-commutes misconception, 18 unchanged.
Not fixed
Arithmetic only. An algebraic final answer — x=5 where 5 is expected — is still marked wrong.

“Got it” skipped a question that was never answered

#31FR-1214
He saw
Tapping “Got it” without attempting the question moved the lesson on, as if it had been answered correctly.
Actually wrong
Not a grading bypass — the server was never fooled. That acknowledgement never reaches grading at all; it is sent as an ordinary chat turn. Nothing stopped the model from reading it as licence to move past a question it had never seen an answer to.
Changed
The chat now works out from the transcript itself which pushed question still has no matching “the student answered…” event. If “Got it” fires while one is open, it is caught in the browser — before any network call — and the student is told to try it first. Deterministic, not a prompt instruction, and it costs nothing.
Note
A student who submits a real wrong answer and then taps “Got it” was never the bug — that already went through grading correctly, and still does.

The last explanation was taken away before it could be read

#28FR-1218
He saw
On the final question of a lesson, the report appeared instead of the explanation.
Actually wrong
The explanation did render — and was then replaced. Three separate auto-advance timers (the tutor's own closing directive, a hit turn cap, and review mode reaching its turn count) each jumped to the report on a fixed 2.2–2.5 second delay, with no student action in between. “The refutation reaches the student” had been marked verified on the strength of it rendering at all.
Changed
All three timers removed. They now only arm the header's “Finish lesson” button and a matching in-chat chip. The report is reachable exclusively by a tap, and the tutor's own closing line was rewritten to say the lesson is over rather than to end it.
Not proven
Confirmed by reading the diff — all three call sites now only set state — not by driving a full multi-turn lesson to its closing recap. That needs a live session nobody has run.

Every lesson opened by telling the student they understood nothing

#30FR-1009
He saw
Starting a new lesson felt discouraging — the tutor opened apologetically, “let's rebuild it from the very first brick”.
Actually wrong
Two independent copies of the same false premise, and either alone reproduced it. The tutor's system prompt asserted on every learn session that the student “understood NOTHING”, including a lesson never attempted — and hardcoded their grade as “10” regardless of the real record. Separately, a hidden message was sent to the model as if the student had typed it: “I understood NOTHING… teach me from zero.”
Changed
Both replaced with copy keyed to the same five-stage mastery banding the progress ramp already uses, so a first-time lesson opens as something new to explore rather than as a failure to repair. The grade now comes from the student's actual row.
Proof
Checked live against the development database at all three reachable stages — never attempted, attempted, mastered — for both the system prompt and the hidden message.

Arabic was rendering to English-subject students in about thirteen places

#20 #41FR-208
He saw
Teaching copy mixing Arabic and English, on a build whose whole point is that it is the English one.
Actually wrong
Structural, not cosmetic. debug and mode flags were standing in for a language check across the chat, lesson, report and practice components — so instrumentation state was deciding which language a child read. One component the first sweep missed rendered a hardcoded Arabic button with no English form at all, and an unconditional right-to-left direction, on the English maths surface.
Changed
Language is now its own prop, independent of the instrumentation axis, defaulting to English. Threaded through every affected component.
Not fixed
This constrains the app's own hardcoded strings. It does nothing about what the model generates in free text, and the evaluation harness that would check that does not exist yet.

“brafo”, “brofa” and friends

#26
He saw
Encouragement copy with misspelt variations of “bravo”.
Actually wrong
There was no typo to find. The English maths language contract instructed the model to sprinkle transliterated Egyptian-Arabic interjections — برافو, يلا بينا — into its replies. The model's own inconsistent transliteration of برافو is exactly where “brafo” and “brofa” came from. Searching for a misspelt string would never have found it.
Changed
The instruction is removed from the English maths contract. The Arabic subject contracts keep theirs untouched — there the interjections are the voice, and no Arabic-capable surface may be removed to ship English first.

The tutor talked about the student instead of to them

#16 #19
He saw
The tutor referring to the student in the third person, and a check-in button reading “I'm lost”.
Actually wrong
The system prompt framed the conversation about the student rather than to them. Separately, the “teach me from scratch” button read literally “I'm lost”, with the Arabic gloss “مش فاهم حاجة” displayed beside it even in English mode.
Changed
The prompt addresses the student directly. The button reads “Walk me through it”, with no Arabic gloss on the English surface.
Not proven
The first-person fix was verified live on /spine. The same fix at the /student lesson call site is the same change in a different place, and was not independently re-checked.

A widget question printed its own question twice

ADR-0009
Seen in review
A stored construction question showed its stem typeset by the card, and again directly underneath as raw LaTeX — “Circle $M$ has radius $5$…” — beneath a Submit button that could never enable.
Actually wrong
The card passed its own stem into the widget as the widget's prompt. And a widget has nothing to submit: the construction is the answer and posts itself, so the Submit button sat permanently disabled, which reads as a broken page rather than as “not applicable”.
Changed
The card tells the widget it has already shown the question. This could not be done by passing an empty prompt: validation treats a blank string as absent and substitutes a generic default, so prompt: "" produced “Construct a radius” — a shortened duplicate instead of silence. Silence had to be asked for explicitly, and applied after validation.
Then found
Hiding the button row took the card's only error surface with it — the failure message lived inside it. A widget attempt that failed to post reported nothing at all, leaving a construction that looked accepted and had not been recorded. The message now belongs to the card, not to the button.

Mastery on the check-in was carried by colour alone

#42FR-1003
He asked for
The raw percentage off the study page — a number like “30%” is discouraging and, turn to turn, confusing.
Actually wrong
The percentage came off, and every other non-colour signal came off with it, leaving four coloured segments and a screen-reader label. Of the three channels the requirement exists to protect — greyscale, colour-vision deficiency, screen reader — only the last was covered. The measurements are below.
Changed
Each segment takes a 3px ink outline, which makes lit-versus-unlit a fill-versus-empty difference rather than a difference in hue, and the band name renders underneath in words. The screen-reader label now names the band too, not just the step count.
Resolved
The triage note framed this as “amend the requirement or revert the code”. Neither was needed: what the feedback objected to is the number, and the requirement asks for a named band. Both hold at once. No percentage returns anywhere on the card.

Voice is pulled from the lesson

#21
He asked for
Voice removed for now.
Changed
The toggle and the microphone are gone from the lesson interface, behind a single flag. The backend — speech synthesis, the provider abstraction, the disk cache — stays wired and dormant rather than deleted, so bringing it back is a one-line flip and not a rebuild.

The traceability counts had never once been generated

Found
While updating the requirements for this release.
Actually wrong
The script that regenerates the requirement counts searched for a section heading that does not exist in the document — its own error message names the correct one, so a rename had changed the message and not the literal. Two consequences, both live: the counts table had been hand-maintained all along and had drifted (it claimed 90 requirements and 84 of 135 tasks; the artifacts say 96 traced and 99 of 143), and the command returned a failure code on every run. Continuous integration runs it as the first line of a fail-fast block, so the traceability job would have gone red the moment this release was pushed — for a reason having nothing to do with the release.
Changed
One-word fix to the heading it looks for; the block is now generated for the first time. Running it twice is a no-op, which is what the integration check is actually asserting.

Four requirements that said VERIFIED and were not

The matrix defines VERIFIED as “someone ran it”, and its own counting rule says to be willing to demote. This is the first time that rule has been exercised. In every case the claim was true of the surface somebody had looked at, and false somewhere nobody had.

FR-208English default
Was claimedThe check-in, plan and dashboard lead in English.
Was trueThose three pages did. Thirteen other places rendered Arabic unconditionally, because an instrumentation flag was standing in for a language check.
FR-1009No “you're behind”
Was claimedBand names are factual; no ranking surface exists.
Was trueOf the interface, yes. The tutor's own prompt told the model every single session that the student understood nothing.
FR-1214Server decides meaning
Was claimedGrading is server-side; the client's own correctness flag is used only for local feedback.
Was trueExactly that, and it was not the vulnerable part. The model was reading an unstructured acknowledgement as an answer, which the requirement never addressed.
FR-1218Refutation reaches the student
Was claimedReturned and rendered under “why that happened”.
Was trueIt rendered, then three timers replaced it with the report 2.2 seconds later. “Reaches the student” has to mean stays on screen.
FR-C03Deterministic grading
Was claimed56 unit tests; a live mastery walk end to end.
Was trueAll of it, and the grader still read 3x6 as 3. The tests tested what the author thought a student would type.

Noor Play replaces Master

The design reversal shipped on 16 September with the note “no ADR yet for this reversal — pending Samuel's confirmation”, and had been sitting unconfirmed since. Authorising this release is that confirmation, so it is now ADR-0011.

Why the original reason stopped holding

#38 #37ADR-0011
Original call
Master, the restrained 15–18 variant. The reason was specific: the variable under test in this environment is the mastery model, and a sticker-heavy visual language would be a second variable sitting on top of it.
What changed
That is an argument about a controlled experiment, and ADR-0010 dissolved the experiment — cross-solution parity was withdrawn, and the comparison became an observational judgement from live usage. There is no longer a control to confound. Meanwhile the PRD's own owner asked for the children's variant, and Prep-3 students are 14–15, inside both published age bands, so the band boundary decides nothing and someone has to.
Implemented
A token, colour, typography and motion layer scoped to the comparison build. Blanket radius and border rules mean any plain utility class picks up the sticker treatment with no component touched, which is what kept the change additive — the component pass adds press, shadow and animation classes to real controls and removes nothing. The product is called Noor throughout.
Checked
The no-red rule holds: the grey-purple that replaced the warning colour is #5a5570, and the only warm hues in the palette are ambers. No Arabic-capable surface was removed. The frozen baseline is untouched.
Cost accepted
Nobody will be able to attribute a difference in outcomes to the mastery model alone. Paid knowingly — a design the audience rejects produces no usage to observe.
Out of scope
The internal surfaces never got the pass and were never meant to. One measured consequence of the token swap: a divider colour is now invisible against the warm card fill (1.00:1), surviving only on internal pages. Against the widget grids it is 1.19:1, against 1.18:1 before — unchanged, so not a regression this introduced.

What this release does not fix

Ten issues closing reads like progress. Twenty-seven are still open, and one of them is the core bet.

Seven issues · the largest item in the feedback

The tutor explains where it should elicit

No Socratic method, no open-ended questions, doesn't end on retrieval; commits to an idea without asking the student to try first; never asks for intermediate steps; can't follow working without a final answer; explanations not chunked; locked to the book's single approach; drifts back to the previous question. Seven reports, one cause. This is the success criterion the whole build exists to test, and nothing in this release touches it.

Three issues · unmitigated

The internal surfaces have no gate at all

The pipeline, content, evidence-walk, admin and developer pages have no environment check and no authentication, and the front page links to two of them. Access control in front of the deployment is the only thing holding them, and that is not a permission model.

Not on anyone's list

The tutor assumes every student is male

Twenty-three masculine pronouns in the lesson prompts alone, more elsewhere, and a masculine Arabic form offered to the model as a worked example. There is no gender column in the database. A girl using this is described to the model as “he”, and the model will follow.

Blocked, not deferred

Resuming a lesson needs accounts first

Student identity today is a per-environment database sequence that a routine content reload truncates and restarts, bound to a cookie the code itself documents as “not an identity claim and not a security boundary”. Hanging real lesson history off it would mean history that a maintenance operation silently deletes. The same precondition blocks per-student analytics.

Solution: Student MVP · branch PDR1-0 · English, mathematics only, Bayesian Knowledge Tracing. Versioned independently of the frozen family-tutor baseline.
