## In plain English

I took a copy of the local database that holds the Prep-3 bank and put it where production is today (v0.11.1), loaded the catalogue the way v0.11.1's deploy does, and took a full snapshot. I then did what the v0.12.0 deploy will do to it: applied migrations 033–039, then ran the new every-deploy catalogue step, twice. I compared the snapshots row by row.

- The catalogue gained exactly the **six `t2u3-1-2` entries** (97 ids to 103), each with a four-step refutation. **No id was removed or renamed.** All 97 existing entries and their 97 refutation rows are byte-identical, including `created_at` and the `reviewed=false` flags.
- Distractor stamps went from **643 to 650**: exactly the **seven** options the six new entries map, on five questions (`q:t2u3-1-2:001`, `002`, `003`, `005`, `006`). Every other stamp is identical. Widget diagnostics are untouched.
- **Every misconception id a student has recorded still resolves** (17 distinct ids across attempts and analytics events, including 12 of the 26 entries feature 003 touched and the grandfathered `mc:divides-reversed`). No student row changed.
- The second run of the new catalogue step, and a whole second deploy (migrations then load), changed nothing at all.
- The rollback paths work: deploying v0.11.1 back over the upgraded database leaves it as it was; the `.down.sql` files for 039 down to 033 run cleanly; rolling forward again lands on exactly the upgraded state.

The six new entries are the only visible product change from the catalogue: a student who picks `$0$` on `q:t2u3-1-2:003` (the key is D) used to get a plain "not quite" with no diagnosis; after the deploy they get `mc:t2u3-1-2:assumed-mutually-exclusive` and its refutation.

## Things to know

1. **Migration 035 changes review stamps on the same deploy.** It is documented (Samuel's answers 33 and 37), changes no status, and shows nothing new to a student. On the copy, for Prep-3 maths: 421 questions that carried `ai dual-check (pending Samuel)` now have `reviewed_by` NULL and `ai_checked_by = 'ai dual-check'`; 29 that carried `local-dev` now have `reviewed_by` NULL and `review_note = 'promoted without review: local-dev'`. 483 Social Studies and 10 Arabic rows are re-stamped the same way. After 035, **all 943 live book questions have no human stamp** (before: 0 of 943 unstamped), so the console's review backlog jumps accordingly. The strings on the real database may differ from this local copy's; the structure of the effect is the migration's header. This is why check 11 is worded as it is: every column other than the seven review-stamp columns (`reviewed_by`, `reviewed_at`, `ai_checked_by`, `ai_checked_at`, `hold_reason`, `review_note`, `parent_kind`) is identical on all 2,111 questions, and the only change to `choices` is the five questions' `misconception_id` stamps.
2. **The live widget diagnostics will differ from the committed widget bundle after this deploy, by design.** `widget-questions.json` in HEAD no longer carries 14 widget predicate-to-misconception mappings that could never fire (recorded in `seed/generated/widget-questions.corrections.json`, which says the change "needs a data migration like 032, in a release"). Migrations 033–039 contain none, and the deploy only loads the widget bundle when it is missing, so production keeps the 14 dead mappings. They are harmless (they cannot fire, and every id they name still resolves). `export_generated_content.py --course course:prep3-math-en --check` against the upgraded copy reports `widget-questions.json` would change (14 of 48 records, `choices.diagnostics` only); the catalogue and the generated-questions bundle round-trip unchanged. Worth knowing before someone re-exports from production and wonders why the diff is not empty.
3. **`rollback/039-review-gate-working-flag.down.sql` is not safe to re-run after `036`'s down has dropped `review_decisions`.** Run in the documented order (039 first, once) it is clean. Run a second time after the full sequence, it fails at its `$verify$` block with `relation "public.review_decisions" does not exist`, because `'public.review_decisions'::regclass` is evaluated even though the `to_regclass(...) IS NOT NULL` test is false. Its header promises idempotence. Low severity; the likely fix is to compare with `conrelid = to_regclass('public.review_decisions')` (null-safe). I did not edit the file.
4. **`kind` is a file-only field.** The `misconceptions` table has no `kind` or `aliases` column, so those parts of FR-4409 are properties of the committed catalogue and the export, not of the live database. Against v0.11.1's catalogue file: 19 existing entries change `kind` from `conceptual` to `generated_distractor`; 26 existing entries gain 28 aliases (the file holds 29 in all, one was already there); no alias was lost; no alias is itself a live id. The local database holds none of the 29 alias ids as rows and no question option stamped with one, so the loader's fold did nothing ("generator aliases found in the database: 0"), as the T423 CI proof also expects. I cannot see production's database (see "Not done"), so check 14 shows what happens if it differs.

The copy's content already equalled v0.11.1's catalogue (97 entries, 97 refutations).

## Method

Everything ran against scratch databases named `ainext_rehearsal_t424_*`, with `AINEXT_DB_DSN` set explicitly on every loader command (`host=127.0.0.1 port=5432 dbname=<scratch> user=<local superuser>`).

```
# copy (not createdb -T)
createdb ainext_rehearsal_t424_upgrade
pg_dump ainext_mvp1 | psql -d ainext_rehearsal_t424_upgrade

# the old build: a detached worktree of the tag, removed at the end
git worktree add --detach $SCR/v0111 v0.11.1

# migrations, exactly as the deploy applies them (tree's own apply-migrations.sh)
git archive v0.11.1 db deploy/apply-migrations.sh | tar -x -C $SCR/v0111-tree
git archive HEAD    db deploy/apply-migrations.sh | tar -x -C $SCR/head
PGHOST=127.0.0.1 PGUSER=<local superuser> sh scripts/ci-migrations.sh apply <tree> <db>

# v0.11.1's every-deploy step (ci-cd.yml at v0.11.1), in the worktree's services/extraction
AINEXT_ENVIRONMENT=mvp1 AINEXT_DB_DSN=... python load_misconceptions.py seed/generated/misconceptions.json

# v0.12.0's every-deploy step: the same shell as ci-cd.yml's "Misconception catalogue (every deploy — idempotent,
# per loaded course)", with only the compose plumbing swapped for the local equivalents. It asks the loader's own
# book_config for "<course> <catalogue>" pairs (exactly one: course:prep3-math-en), checks the course node is
# loaded, and runs  load_misconceptions.py <repo>/services/extraction/seed/generated/misconceptions.json
```

Python was `services/extraction/.venv`, whose `psycopg 3.3.4` and `pydantic 2.13.4` are the pins in `deploy/Dockerfile.loader`. `PYTHONDONTWRITEBYTECODE=1` throughout.

Snapshots (`snap.py`, in the session scratchpad, not committed) record: every misconception row; every explanation_library row (`to_jsonb`); every question row (`to_jsonb`); every distractor stamp (MCQ options, `options` shells and widget `diagnostics`, as question, kind, position, key or predicate, text, id); visuals; graph nodes, edges and `node_subject` digests; attempts; students; and every `mc:` id found in any non-content table. A second script compares question rows column by column per course.

Differences from production, stated so nobody over-reads the result:

- Loader and migrations ran as the local superuser, not `ainext_maint`/the box's owner. Both bypass RLS, and the loader's SQL is the same.
- The role-password step (3a' in `apply-migrations.sh`) did not run (`AINEXT_*_PASSWORD` unset, deliberately: the roles are cluster-wide and shared with other local databases). Migration 017 re-asserts the three roles' attributes, which are identical to what is there.
- The one-time deploy steps were evaluated, not run, because their gates say they would do nothing here: operators exist (2); all three National courses are present by id; the generated-maths gate reports 0 of 591 bundle questions absent. The app and console were not started.
